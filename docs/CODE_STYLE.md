# Стиль кода

Основа — [официальный стиль GDScript](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/gdscript_styleguide.html). Ниже — правила проекта поверх него. Форматирование и большая часть именования проверяются автоматически: `make check`.

## Язык

- Идентификаторы (классы, функции, переменные, сигналы, файлы, ключи данных) — на английском. Соответствие игровых терминов и имён в коде — в [GLOSSARY.md](GLOSSARY.md).
- Комментарии, doc-комментарии (`##`) и документация — на русском.

## Типизация

- Каждая переменная, параметр и возвращаемое значение типизированы. Можно выводить тип через `:=`, когда он очевиден справа.
- Коллекции — типизированные: `Array[Item]`, `Dictionary[StringName, float]`.
- Предупреждение `untyped_declaration` настроено в проекте как ошибка; `unsafe_*` — как предупреждения, их тоже нужно устранять.

## Именование

| Что | Стиль | Пример |
| --- | --- | --- |
| Файлы, папки | snake_case | `stat_block.gd` |
| Классы (`class_name`) | PascalCase | `StatBlock` |
| Функции, переменные | snake_case | `apply_modifier()` |
| Приватное | префикс `_` | `_cached_total` |
| Константы, значения enum | CONSTANT_CASE | `MAX_SKILL_LEVEL` |
| Сигналы | глагол в прошедшем времени | `item_equipped` |
| Обработчики сигналов | `_on_<источник>_<сигнал>` | `_on_inventory_item_added` |
| Идентификаторы контента | `StringName`, snake_case | `&"fire_damage"` |

Имя файла совпадает с `class_name` в snake_case. Один публичный класс на файл.

## Структура файла

Порядок проверяет `gdlint`: `class_name` → `extends` → doc-комментарий → сигналы → enum → константы → `@export` → публичные переменные → приватные → `@onready` → методы движка (`_ready`, `_process`…) → публичные методы → приватные.

## Форматирование

- Табы, длина строки — до 100 символов. Формат делает `make format` (gdformat); вручную не выравнивать.
- Магические числа баланса — не в коде, а в данных или именованных константах.

## Практики

- Классы в `src/core/` наследуют `RefCounted` или `Resource`, не `Node`.
- Случайность — через переданный `RandomNumberGenerator`, не глобальные `randi()`/`randf()`.
- Ошибки разработчика — `assert()` / `push_error()`; не глотать молча.
- Сигналы для событий «вверх», прямые вызовы «вниз». `get_node` по длинным путям не использовать; ссылки на дочерние узлы — через `@onready` или `%UniqueName`.
- Комментарий объясняет «почему», а не пересказывает код.

## Тесты

- Тест-файл: `tests/<путь как в src>/test_<имя>.gd`, `extends TestCase`.
- Тест-методы начинаются с `test_`. Для каждого создаётся новый экземпляр класса; раннер вызывает `before_each()`, тест-метод и `after_each()` — последний и после неудачных проверок. В `after_each()` освобождать ноды, созданные в `before_each()`. Проверки — `assert_eq`, `assert_true`, `assert_false`, `assert_almost_eq`.
- Тестировать `src/core/` обязательно, сцены — по необходимости.
- Любая ошибка движка или скрипта (`push_error`, вызов у `null`, ошибка компиляции зависимости) во время теста, включая `before_each()` и `after_each()`, делает его проваленным; предупреждения — нет.
